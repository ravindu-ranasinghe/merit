# Arc batching makes Merit easier to use

**Build atomic bounty funding on Arc, then make Streams recovery demonstrable.** QuickNode already matters: it supplies the confirmed events that advance Merit's payment state, discovery, earnings, and receipts. It does not secure the escrow or judge reviews, and a well-built RPC indexer could replace it. The strongest newly verified Arc improvement combines USDC approval and bounty creation into one transaction using Arc's sender-preserving batch facility. A read-only simulation against the existing deployed escrow succeeded; a browser-wallet transaction remains untested. These changes offer a clearer hackathon story while preserving the deployed contract.

Research date: November 15, 2026. This assessment combines current official documentation, local source inspection, and a read-only Arc testnet simulation. No application code, deployed settings, or funds changed.

## Streams supplies payment state, while escrow secures funds

The backend authenticates Streams deliveries, checks the escrow address, stores unique logs, and rebuilds each affected bounty's status. Without new indexed events, funding remains pending and new approvals, payouts, and refunds stop appearing correctly. Public discovery, receipts, and reviewer earnings consequently become stale. The escrow still holds funds and enforces its rules independently; direct contract transactions remain possible. These roles are visible in the [receiver](/Users/ravi/Documents/merit/backend/src/streams/webhook.ts:43), [projector](/Users/ravi/Documents/merit/backend/src/streams/project.ts:17), and [escrow](/Users/ravi/Documents/merit/contracts/src/BountyEscrow.sol:82).

**Streams is useful managed infrastructure, rather than an irreplaceable payment primitive.** A checkpointed RPC log poller could supply the same data at this scale, but would need retries, cursors, catch-up, deduplication, and a chain-history policy. That comparison follows from the available [RPC log filtering](https://www.quicknode.com/docs/ethereum/eth_getLogs) and [Streams historical backfill](https://www.quicknode.com/docs/streams/backfilling). Browser pages still poll Merit's API, so describe the present architecture as chain-to-backend push. The contract prevents double payouts; database uniqueness prevents duplicate ledger entries. Neither establishes that a review was useful.

## Arc can remove one funding transaction today

Today's frontend sends USDC approval and bounty creation separately. Ordinary multicall would change the caller seen by the escrow, breaking the original funder identity. Arc's **Multicall3From** preserves that identity through its CallFrom facility. Its direct-EOA restriction matters: this is an optional EOA funding path, with the existing flow retained for unsupported accounts. See [Arc batching semantics](https://docs.arc.io/arc/concepts/batched-transactions) and the [deployed testnet tutorial](https://docs.arc.io/arc/tutorials/batch-usdc-transfers).

The researcher verified deployed bytecode and simulated the exact sequence: approve the existing escrow for 1 USDC, create a bounty, then read that transient bounty. All subcalls succeeded; the stored funder matched the original EOA. The initial allowance was zero. **No transaction was broadcast**, no state persisted, and the exact latest-block number was not recorded. The [research notes](</Users/ravi/Documents/merit/research_notes/Arc and Streams product depth/arc.md>) include reproducible code and addresses.

Implementation should require both calls to succeed atomically, approve the escrow as spender, and retain the existing event parser. Wallet execution, rollback with existing allowance, and fresh Streams ingestion still need tests. The rough estimate is **4–8 engineering hours**, conditional on wallet compatibility. This uses an Arc-specific capability to remove a real user step without changing the escrow ABI or backend approval authority. USDC gas also keeps reward and fee units familiar; do not promise a fixed fee or confuse chain finality with full application latency. [Arc fee design](https://docs.arc.io/arc/concepts/stable-fee-design)

## Deeper Streams value means useful actions and recovery

The best next Streams feature is a personal action inbox derived from confirmed events: ready to claim, payment confirmed, and refund confirmed. Consumers should see clear next actions and syncing status. Operators can separately inspect stream progress and bounded replay results. A useful staging demonstration would recover missed historical payment events, replay an overlapping range, and show unchanged earnings without duplicate alerts. Chain replay rebuilds payment projections for existing bounty metadata; it cannot recreate GitHub evidence or offchain identity mappings. [Backfill capabilities](https://www.quicknode.com/docs/streams/backfilling)

Budget roughly **4–8 hours each** for a small inbox and a bounded recovery demonstration. External notifications require durable work records and replay suppression. Streams retries can ultimately pause; consumers must acknowledge safely and recover. Event age alone cannot detect an outage because an escrow can be quiet. Current ingestion also lacks reorg replacement handling. [Webhook delivery](https://www.quicknode.com/docs/streams/destinations/webhooks), [reorg handling](https://www.quicknode.com/docs/streams/reorg-handling)

## Sponsored claims are a larger follow-up

An unrelated relayer cannot claim today's rewards: [claim requires the approved recipient as caller](/Users/ravi/Documents/merit/contracts/src/BountyEscrow.sol:124). Circle supports sponsored Arc testnet transactions through smart contract accounts, but Merit's current wallet-link verification handles EOAs. A user-controlled smart wallet would need compatible signature verification, execution, and new recipient onboarding. Existing approved EOA rewards cannot simply change recipients. This is a **1–2 focused day estimate after a compatibility spike**, rather than a quick backend relayer. Sponsorship means the developer pays gas; paying gas in USDC alone is different. [Circle Gas Station](https://developers.circle.com/wallets/gas-station), [Viem verification](https://viem.sh/docs/actions/public/verifyMessage)

The supplied guide rewards reduced crypto friction, useful event-driven actions, technical execution, and demo quality (pages 8, 10, 13, 18). Atomic funding plus a real settlement-and-recovery demonstration fits those aims. Before extending scope, capture a fresh event through the enabled Streams filter: the [backend notes still mark that proof pending](/Users/ravi/Documents/merit/backend/README.md:189). No feature guarantees a prize.
